# Table preparation groups

Live Orders groups NEW table orders within the authenticated restaurant, exact table ID and exact TableSession ID. Table numbers alone never determine membership. Takeaway, completed/history orders, legacy ACCEPTED and older unbatched PREPARING orders remain individual.

The optional `Order.preparationBatchId` freezes membership when staff starts preparation. It is an operational identifier, not an Order number or a new collection. Reloads preserve the PREPARING card; later NEW orders form another card and receive a different ID when started. No data migration, new index, dependency or environment variable is required. Existing table-session indexes bound the lookup to one visit (customer submissions are limited to 100 per visit).

Hot-reload regression: a previously compiled Mongoose Order model could lack `preparationBatchId`. Default strict updates silently stripped that field while saving PREPARING, so refetch rebuilt separate cards. Order initialization now replaces only a cached model missing this path (without changing its collection). Group writes reject unknown fields and verify the persisted status and batch ID of every member before committing. Tests reproduce the stale-schema failure and verify rollback, cache refresh, one PREPARING card after realtime refetch/reload, and one shared ready action. Existing PREPARING records with no batch ID remain individual; their original grouping cannot safely be inferred.

`PATCH /api/dashboard/orders/preparation` accepts a strict payload containing `orderIds`, `expectedStatus` and `status`. The server derives the restaurant from Auth.js, derives table/session scope from an owned anchor order, verifies every supplied ID in that scope, and rejects takeaway, foreign members, stale statuses and mixed preparation batches. Allowed transitions are NEW → PREPARING and PREPARING → READY.

A snapshot transaction writes the visit version before selecting membership, serializing with customer submission and session closure. A new order committed before that boundary is included, even if the staff snapshot did not yet show it; one committed afterward stays NEW. Any supplied order that was cancelled or changed causes a conflict and no partial transition. PREPARING requires the full current batch membership. The single-order endpoint cannot update batched orders, preventing a stale client from splitting a preparation batch. Cancellation remains individual and available for NEW orders through More actions.

All members receive the same transition timestamp. Expected-status updates and transaction retries ensure competing staff actions cannot partially win. Conflicts trigger authoritative refetch and the existing localized feedback. One minimal `{version: 1}` realtime invalidation is published after commit to the restaurant and customer visit; publishing failure cannot roll back the database result. Existing reconnect, polling and sound deduplication are unchanged.

Each original order retains its own visible number, age/time, items, notes and subtotal inside the operational card. Items are deliberately not aggregated, even when identical, so options, removals and instructions remain attached to their original snapshot and order. Only the preparation action is shared. Customer DTOs do not include batch IDs. Final Bill, customer history, recent history and analytics still read/count individual Orders, and READY does not close the TableSession.

Verification covers three-order grouping; table/session/tenant/takeaway boundaries; legacy handling; snapshots and customization; stale and simultaneous actions; cancellation; late arrivals; post-commit invalidations; individual totals/history; and a two-customer Table 7 browser flow with Arabic, Hebrew, English, RTL and responsive layouts.

Manual test: submit two orders from two browsers at the same table. Confirm one NEW card, start once, and reload to confirm one PREPARING card. Submit a third order and confirm it remains separately NEW. Mark the first group ready; check that only its two orders leave the queue, history shows them individually, and Final Bill retains all three original orders and totals.
